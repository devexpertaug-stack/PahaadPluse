# The Forest Season Resort demo: generated home-property dataset, demo auth, live-first dashboard (v1)

The cluster is re-centered on **The Forest Season Resort** (`mus-forestseason`) as the Home_Property, backed by a deterministic seeded generator that produces 52 reviews across all five platforms over ~18 months and feeds them through the real `ReviewParser` + `enrich` ingestion pipeline. A demo auth service (argon2 hashing, HMAC-signed ~12h tokens, lockout) gates the dashboard, which was reworked to render strictly live backend data with honest loading/empty/error states — all nine baked snapshots were deleted. The user asked for live "scraping"; the team deliberately did **not** scrape the live platforms (no free credential-less path that honours each platform's terms) and documented this transparently in the datasheet and README, offering free live-URL options (Codespaces / Vercel+free backend / tunnel) with no paid cloud provisioning.

Watch for: data endpoints are intentionally left ungated — only `/auth/*` is enforced, and the token's `property_id` scope is never checked by any data route (confirmed, disclosed). The HMAC `session_secret` defaults to a committed placeholder and the Codespaces "fastest free URL" path doesn't instruct rotating it, so a public Codespaces demo issues forgeable tokens (possible). Everything else — honesty framing, re-centering coherence, test quality — holds up.

**Verdict**: APPROVED

## High-level view

The honesty framing is the central question and it is handled well. The datasheet and README state plainly that live crawling is not performed, explain why (no free credential-less path, platform terms, robots.txt gating via `responsible.py`), and label the dataset as generated-and-ingested rather than scraped. Nothing is presented as a verbatim scrape; the generated file is additionally posted through the real `POST /market-radar/collection/upload` path so the "collection" claim is demonstrated end to end, not asserted.

Auth is genuinely functional and safe-for-demo. Passwords are stored only as argon2 hashes, tokens are HMAC-signed with an embedded expiry and rejected when tampered or expired, wrong/unknown credentials return 401, and five failures lock the account. The deliberate thin spot is that only `/auth/*` is gated — every data endpoint stays open and no route enforces the token's property scope. This is disclosed in both the router docstring and README, and is acceptable for a demo, but it means the login is a UI gate, not an authorization boundary.

The home-property re-centering is coherent across analytics, sentinel, concierge, destination and time-machine: all point at `mus-forestseason`, concierge facts were rewritten to resort-specific content (including a pool→pets swap), and the existing tests were updated to the new ids rather than weakened. The live-first dashboard rework removed all snapshots and routes every page through a shared `useLiveData` + `LoadState` pair, so an unreachable backend shows an honest error panel instead of stale data — and a dedicated test rejects the API and asserts exactly that.

The one deployment-security wrinkle: `session_secret` defaults to the committed `dev-only-...-change-me` string, which `make demo` uses as-is. The README's Vercel option tells you to set a strong secret, but the Codespaces option (billed as the fastest free public URL) does not, so a public Codespaces demo signs tokens with a secret anyone can read from the repo.

### Honest "scraping": generated, ingested, and labelled as such

The user literally asked to "scrape" the Forest Season Resort. The implementation does not scrape and says so, in the two places a reviewer and a user would look. `forest_season_reviews.py` opens with a honesty note explaining the environment "cannot (and must not) crawl the live review platforms — doing so has no free, credential-less path and would breach each platform's terms," and the datasheet's collection-method section says the same with the platform names spelled out and a pointer to the `responsible.py` robots.txt/terms gating. The README's "Is this real scraped data?" section repeats it without hedging and the top of the README links to it. This is the honest resolution of a request that could not be fulfilled as literally stated, not a scrape dressed up as synthetic.

What makes the framing credible rather than a disclaimer: the generated dataset is run through the *same* `ReviewParser` + `enrich` pipeline as any collected review (`build_review_records` splices `generate_forest_season_seed()` ahead of the hand-authored competitor rows), and `test_generated_resort_file_ingests_via_upload_endpoint` posts the generated TripAdvisor rows through `POST /market-radar/collection/upload`, asserts `new_count == len(rows)`, then re-posts the identical file and asserts `new_count == 0`. That second assertion proves the real collector keyed and deduped the records rather than blindly appending — the "live collection path" claim is demonstrated, not just stated.

The generator itself is pure and seeded (`FOREST_SEASON_SEED = 20240915`), and `test_generator_is_deterministic` checks both that the same seed reproduces identical records and that a different seed diverges. The datasheet counts (82 total, 52 for the resort, platform split 12/10/9/11/10, 10 missing-URL records) match what the generator actually emits — verified by running `build_review_records()`. Determinism is what keeps the datasheet's auto-generated counts honest over time.

### Auth: hashing, token integrity, and the enforcement gap

Passwords never touch storage in plaintext: `hash_password` uses passlib's argon2 context and the seeded demo users store only the `$argon2id$...` string (`test_demo_credentials_are_seeded` asserts the stored hash starts with `$argon2` and that `verify_password` round-trips). Tokens are a `<payload>.<signature>` pair where the signature is HMAC-SHA256 over the payload keyed on `session_secret`, compared in constant time, with an embedded `exp`. `test_session_token_roundtrip_and_expiry` confirms a tampered token (`token + "x"`), garbage, and an already-expired token all return `None`. Login returns a resort-scoped `PublicUser`, wrong and unknown credentials both 401 (same error, avoiding user enumeration), and `test_lockout_after_repeated_failures` drives five failures on an isolated service and confirms even the correct password is then refused with `AccountLockedError`.

The gap is authorization, not authentication. The router docstring and README both state that only `/health` and the WhatsApp webhook are public "in intent," but in practice every market-radar / sentinel / concierge / destination / minimal endpoint is reachable with no token at all — `get_current_user` is only wired into `/auth/me`. The token carries `property_id`, but no data route reads it, so the "resort-scoped user" scope is cosmetic. For a single-property demo this is fine and it is disclosed, but it should not be read as tenant isolation: the login gates the UI, not the data.

```
browser → /auth/login → signed token (carries property_id)      ← enforced
browser → /market-radar/..., /sentinel/..., /concierge/...        ← NOT enforced, property_id ignored
```

A second, smaller wrinkle: `get_auth_service()` is an `@lru_cache` singleton holding mutable `failed_attempts` / `locked_until` on the seeded users. A lockout therefore persists process-wide for 15 minutes and the endpoint tests have to call `_reset_demo_owner()` to stay order-independent. Harmless for the demo, but a locked owner account during a live presentation would stay locked.

### Re-centering coherence

The Home_Property swap from `mus-pineview` to `mus-forestseason` is applied consistently: `analytics_dataset.HOME_PROPERTY_ID`, `sentinel_seed.HOME_PROPERTY_ID`/`NAME`, the concierge `_default_facts` and update fallback, the destination-lens seed rows, and the time-machine intervention log all move together, and the resort is prepended to `PROPERTIES` so `PROPERTIES[0]` is the home. The concierge facts weren't just re-tagged — they were rewritten to resort-specific copy (deodar forest-view breakfast, 10-min drive to Mall Road) and the `fact-pool` entry was replaced with `fact-pets`, which `test_concierge_facts_are_resort_topical` pins by asserting `{"breakfast","checkout","wifi","parking","pets"}` are present. A home-property personality weight (`0.08`) was added so the resort reads as generally well-liked without being the leader. The updated analytics/time-machine/changepoint tests were re-pointed to the new ids rather than deleted, and `test_analytics_endpoints_centre_on_resort` + `test_lifespan_resort_endpoints_populated` assert the live endpoints return the resort as home with populated boards and heatmaps.

### Live-first dashboard with honest failure states

All nine `*Snapshot.json` fixtures are deleted and no non-test file references `Snapshot` anymore (grep confirms). Pages fetch through `useLiveData`, which models `loading | ready | empty | error` and, critically, sets `data` to `null` and `status` to `error` on a rejected fetch — there is no branch that substitutes a baked payload. `LoadState` renders a distinct error card ("Backend unavailable … this view shows live data only, never a stale snapshot") so an unreachable backend looks intentional. The `deep-pages` and `sentinel-destination` tests were rewritten to the live contract: they mock the API with resort-shaped payloads to assert live rendering, then `setApi({...reject})` and assert `findAllByText("Backend unavailable")` **and** `queryByText("market gap")` is absent — i.e. the error path shows the honest panel and specifically does not fall back to the old snapshot theme. These tests would fail if `useLiveData` grew a snapshot fallback or if a page swallowed the rejection.

### Login page, session store, and the free live-URL options

The requested "pretty login page with a nice background" is implemented without an external/copyrighted image: the background is layered CSS gradients plus an inline SVG mountain/forest silhouette, with a glassy branded card, demo-credential autofill, and a documented one-line hook to drop in a real photo later. The user attached an image but it is not present in the repo, so the self-contained SVG background is a reasonable substitute and the swap-in path is documented. `SessionGate` redirects to `/login` when no token is stored; it does not re-validate the token against the backend, so an expired session passes the gate and only fails on the first API call (which 401s but does not auto-redirect) — demo-grade and noted.

The "I need a live URL" request is answered with three zero-cost paths (Codespaces public port, Vercel + free-tier backend, free tunnel) and an explicit statement that no paid AWS/cloud resources are provisioned and there is no infra-as-code spinning up paid services — correctly declining the user's offer to spend AWS credits, consistent with the free constraint. The one gap: the Vercel option instructs setting a strong `SESSION_SECRET`/`PSEUDONYM_SALT`/`PII_ENCRYPTION_KEY`, but the Codespaces option — presented as the fastest public URL — does not, and `make demo` runs with the committed `dev-only-session-secret-change-me` default. On a public Codespaces port that means session tokens are signed with a secret anyone can read from the repo and are therefore forgeable. Adding the same "set SESSION_SECRET" note to Option A closes it.

### Tests exercise real paths

The new suites would fail if the implementation were reverted: the argon2 round-trip asserts a real `$argon2` hash and rejects a wrong password; the token test rejects tampered/expired tokens; the lockout test drives real failures through `AuthService`; the generator test checks determinism and seed-sensitivity; the upload test proves ingestion + dedup through the real collector; and the frontend error-state test rejects the API and asserts the honest panel with no snapshot fallback. None of them assert only static constants or mock away the logic under test. Backend `pytest` (auth + forest-season) is green, `ruff check` is clean, and the frontend `vitest` suite passes 22/22.
