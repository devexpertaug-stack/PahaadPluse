# Vibrant alpine design-system refresh + backend cold-start seed (v1)

Two user asks, two independent changes. The frontend got a design-system overhaul: the three centralised theme files (`tailwind.config.ts`, `globals.css`, `lib/theme.ts`) were re-valued from the old muted forest green to a brighter teal-leaning alpine green, two new accent scales (glacier `sky` blue and cool `slate`) were added, and a real `next/font` pairing (Inter body + Poppins display) was wired in `layout.tsx` — closing a real bug where `--font-sans` was never set and the app silently fell back to `system-ui`. The look propagates through the shared `ui`/`layout`/`charts`/`common` primitives, so all 18 dashboard pages inherit it without per-page edits. The backend change diagnoses "doesn't work" correctly as a run-path problem, not a logic bug: a new `app/seed/warm.py` + `python -m app.seed` entrypoint, a FastAPI lifespan that eagerly warms the in-memory services on startup, and a seed step prepended to `scripts/demo.sh` so a fresh clone's single `make demo` yields a populated dashboard.

Watch for: chart series semantics regressed — "Negative" sentiment and "Complaint %" trends now render in blue/slate instead of a warning red, dropping the intuitive red=bad cue (confirmed). `forest.600` and `forest.700` are set to the identical hex, so button hover/shade steps that rely on the 600/700 gap are flat (confirmed, cosmetic). The DB schema half of the backend fix is a no-op today because no ORM tables exist (confirmed, harmless and documented).

**Verdict**: APPROVED

## High-level view

The palette shift is real and verifiable: the old `#275233 / #1c3725 / #3f8150` forest values are gone from the codebase (grep-confirmed), replaced by a brighter saturated green plus genuinely new blue and slate hues used on badges, stat tiles, table hovers, and chart series — this is a multi-hue system, not one-green-everywhere, and it satisfies the "colourful / mountain vibes / replace the dull green" ask. The three theme files are mutually consistent; every token, CSS var, and palette key the components reference resolves (lint + build pass, including the nested `mist.white` → `bg-mist-white` and the `dawn-ridge` background-image → `bg-dawn-ridge` utilities).

Typography is the strongest single win: `--font-sans`/`--font-display` are now actually set via `next/font/google` and consumed by `globals.css` headings and the display-font classes on primitives, so the app no longer falls back to system fonts. Devanagari coverage is not addressed by either Inter or Poppins, which is called out as acceptable for this pass in the plan.

The backend fix targets the correct failure. Endpoints already returned data in-process; the gap was that nothing eager-seeded on a cold start and `demo.sh` never seeded. The lifespan + explicit seed entrypoint close that, and a cold-start run (DB deleted, seed run twice, then TestClient through the lifespan) returns populated 200s on all 11 data endpoints. The schema-creation path runs but registers no tables since the domain models are pydantic — kept for forward-compat and documented as such.

The main unresolved concern is chart color semantics: swapping red for blue/slate on negative/complaint series makes the dashboard prettier but less legible for the one thing those panels exist to flag.

### Palette re-valuation keeps token names, swaps values

The strategy of preserving Tailwind token names (`forest`, `mist`, `pine`, `dawn`) and `lib/theme.ts` palette keys while re-valuing them is what let an 18-page redesign land with zero per-page edits and zero test churn — `StatTile.test.tsx`'s `text-forest-800` assertion and the chart imports of `palette.forest.*` still resolve unchanged. The new values are a genuine hue shift: forest moves from muted `#275233` to a saturated teal-green `#1f8a5b`, and two scales that didn't exist before — `sky` (`#1d9bd1` glacier blue) and `slate` (`#4b6472`) — are added to all three files in sync. A grep for every old hex (`#275233`, `#1c3725`, `#3f8150`, `#dca24c`, `#9cc3a5`, `#c0563b`, `#21422b`, `#4f8a63`) returns nothing outside the checked-in snapshot fixtures, so no component references a dropped value.

One wrinkle in the scale: `forest.600` and `forest.700` are both `#1f8a5b`. `Button` primary is `bg-forest-600 hover:bg-forest-500`, so its hover still lightens, but anywhere the 600/700 pair is used expecting two distinct shades, they'll look identical.

### Typography wiring fixes a real fallback bug

`layout.tsx` previously never set `--font-sans`, so Tailwind's `font-sans: var(--font-sans)` resolved to nothing and the app rendered in `system-ui`. The change imports Inter (body, `--font-sans`) and Poppins (display, `--font-display`), applies both variable classes on `<html>`, and `globals.css` now sets `body` to `var(--font-sans)` and `h1/h2/h3` to `var(--font-display)`; primitives add `font-display` on card titles, page headers, stat values, table headers, and the sidebar brand. The pairing has no Devanagari coverage, which the product shows in places — the plan explicitly accepts this for this pass, so it's a known limitation, not an oversight.

### Multi-hue propagation, and where it hurts legibility

Badges gained `sky` and `slate` tones; the header "Demo mode" badge and page-header eyebrows moved to `sky`; stat tiles got a `dawn-ridge` gradient top-bar and a lift-on-hover; tables hover `sky-50`. This is the multi-hue breadth the brief asked for.

The cost shows up in the trend charts. `TrendsPanel` previously drew the "Negative" sentiment series and the "Complaint %" series in red (`#c0563b`); they're now `palette.sky.DEFAULT` (blue) and `palette.slate.DEFAULT` (gray) respectively. Nothing is broken, but these two series are the ones a hotelier scans for trouble, and blue/gray no longer carry the "this is the bad line" cue that red did. The forecast page's 80% interval band moving to `sky.bright` is fine; the sentiment/complaint recoloring is the one worth reconsidering. Keeping a dedicated warning hue in the palette for "bad" series would restore the signal without giving up the multi-hue look.

### Backend fix matches the actual failure mode

The diagnosis is right and the task notes are honest about it: every endpoint already returned data in-process because services self-seed behind `@lru_cache` getters, so this was never a logic bug. The real fresh-clone gap was that `create_app()` had no startup hook and `demo.sh` never seeded. `warm.py` adds `warm_services()` (eagerly instantiates all seven process-wide services so the seed runs at startup and any seed error surfaces then, not on first request), `ensure_schema()`, and an idempotent `seed_all()` driven from both the lifespan and `python -m app.seed`. `demo.sh` runs the seed in a subshell before launching uvicorn, preserving `set -euo pipefail`.

Cold-start was reproduced here: deleting `data/pahadpulse.sqlite`, running `python -m app.seed` twice (idempotent, no error), then entering the `TestClient(app)` lifespan returned populated 200s on all 11 data endpoints. `ensure_schema` runs `Base.metadata.create_all` with no ORM tables registered (the domain models are pydantic), so it creates an empty SQLite file and no endpoint reads from it — kept for the moment an ORM model is added, and the docstrings say so plainly. The warming is the part that actually makes the dashboard populated.

```
make demo
  └─ scripts/demo.sh
       ├─ (cd backend && uv run python -m app.seed)   # seed_all(): ensure_schema + warm 7 services
       ├─ uvicorn app.main:app                          # lifespan also runs seed_all() → warm on boot
       └─ next dev (NEXT_PUBLIC_API_BASE_URL wired)
```

The `demo.sh` top-of-file comment still reads "Later features extend this to seed data and run the scripted scenario" — stale now that the seed step is inline. The README section is correctly rewritten.

### Test coverage

The four new tests in `test_seed_startup.py` are meaningful rather than tautological: `test_lifespan_warms_data_endpoints` drives the real `TestClient(app)` lifespan and asserts non-empty bodies across ten endpoints, so reverting the lifespan or the warm step would fail it — it tests the behavior the fix exists to guarantee, not just that functions don't throw. The three idempotency tests cover re-running `ensure_schema`/`warm_services`/`seed_all`, which backs the "safe in `set -e`" claim in `demo.sh`.

Not tested: the frontend has no assertion that the new fonts or palette classes render (vitest coverage stayed at 14 tests, markup assertions unchanged) — acceptable since visual changes aren't unit-testable here, but it means the font wiring and chart recoloring are only verified by build success and manual reasoning, not a test. The chart color semantics regression in particular would not be caught by any existing test.
